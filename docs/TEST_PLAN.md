## 2. How each step runs

All pipeline steps run in GitHub Actions on `main`, through manual (`workflow_dispatch`) workflows, so each result has a run to point to. No token is printed or uploaded; the auth actions mask what they issue.

| Mechanism | Used by | How |
|---|---|---|
| Google identity | All | `google-github-actions/auth`, workload identity federation into the apply identity (`main`) or plan identity (any ref). For H4, the same step with `token_format: access_token` supplies the header's Google token |
| Databricks principal, provider | H2, H3, H6–H8 | Provider `auth_type = "github-oidc"`, `DATABRICKS_CLIENT_ID` = the principal's application ID |
| Databricks principal, direct API | H4, H5, H12, C10 | The job exchanges its GitHub OIDC token for a Databricks token at the account's token endpoint, then calls the Accounts API with that token and `X-Databricks-GCP-SA-Access-Token` |
| Google service account as Databricks user | H1, H10 | Provider `google_service_account` = the apply identity, after it's added to the Databricks account as account admin. Removed again after the step |
| People | H9, Phase B, A5 | Recorded by hand, with screenshots scrubbed of identifiers |

The direct API calls first run against a project that doesn't exist, which shows whether a call gets past authentication without building anything. Then they run for real.

## 7. Findings that change the requirements

| # | Finding | Effect |
|---|---|---|
| R1 | GitHub issued this repository's OIDC tokens with the immutable-ID subject `repo:<owner>@<owner-id>/<repo>@<repo-id>:ref:<ref>`, not `repo:<owner>/<repo>:ref:<ref>` as F5 and §4.2 show. Databricks matches the subject exactly | The configuration guide (E6) tells the reader to take the subject from a real token, or from the `TOKEN_SUBJECT_INVALID` error of a first run, rather than typing it. The ID form is also the safer one: a deleted repository's name can be registered again by someone else; its IDs can't. Google workload identity federation wasn't affected: its conditions use the `repository` and `repository_owner_id` claims, not the subject |
| R2 | Domain restricted sharing (`iam.allowedPolicyMemberDomains` at the organization) refuses the grants classic workspace creation makes to Databricks-owned service accounts. A project-level exception for Databricks' Google customer ID is needed, and it has to be narrowed: alone it admits every Databricks identity in any role. Setting it needs Org Policy Administrator at the organization, which a project owner (the pipeline's apply identity) doesn't have; and the Org Policy API refuses user credentials that name no quota project | The configuration guide (E6) adds a prerequisite owned by the organization's policy administrators, made once per workspace project. Neither GitHub identity can make it |
| R3 | Classic workspace provisioning on GCP makes four kinds of grant to Databricks-owned accounts: the workspace account in two project custom roles and a network custom role, and the regional metastore's storage credential in `storage.objectAdmin` and `storage.insightsCollectorService` on the workspace's default Unity Catalog bucket. A narrowed profile is checked by creating a workspace, since nothing else exercises the Unity Catalog grant |
