Keyless Databricks on GCP

How a GitHub Actions pipeline builds and runs classic-compute Databricks workspaces on Google Cloud with Terraform: own-IdP SSO left on, Private Service Connect front and back end, and no keys or stored secrets. Every claim here was tested in a lab, then the lab was torn down and rebuilt from empty state in one pass to prove it, and built once more on an account with Microsoft Entra ID single sign-on and automatic identity management, where people got workspace access from their Entra groups. Identifiers are placeholders; the reference implementation (E5) is the lab repository.

E4

Recommendation

2026-11-14, after the end-to-end rebuild and the Entra SSO and AIM tests.

Recommendation: Terraform for everything, with a REST provider for the objects that need the Google token header

Manage the whole Databricks on GCP deployment from GitHub Actions with Terraform and keyless federation, SSO left on:

  • The Databricks provider (databricks/databricks, auth github-oidc) for every object it can manage on federation: private access settings, permission assignments, and everything inside workspaces.
  • A generic REST provider (magodo/restful) for the three objects the Databricks provider can't create or update with own-IdP SSO: network configurations, VPC endpoint registrations, and workspaces. It calls the same Accounts API with the automation principal's Databricks token and the apply identity's Google access token in X-Databricks-GCP-SA-Access-Token (H3, H4).
  • Both tokens as Terraform ephemeral variables, minted in the job step that runs Terraform: never in a plan file, state, or log.
  • Private Service Connect with the back end from creation (scenario B in the PSC design) and the front end added once users' DNS is ready.
  • Two runner tiers: GitHub-hosted runners for GCP and account-level stacks (the account API is public); a self-hosted runner inside the network for workspace-level stacks once the workspace's public access is off.

With Entra ID for people (the customer's target; tested, USE_CASE_RESULTS.md):

  • Turn on Entra SSO and AIM. The pipeline above is unaffected by either (U1) and builds the whole private deployment with both on (U2).
  • Workspace access by Entra group, in Terraform: add each group to the account from Entra, then assign it to workspaces (account stack) and give it an entitlement in each workspace (workspace stack). Without the entitlement, members are refused (R18). Nested groups work for membership but can't be managed by Terraform (R17).
  • People reach private workspaces only through the front end; a group member signing in from the internet was refused by the workspace after Entra and the account had accepted the sign-in (U4).
  • Leavers: disable in Entra and revoke their personal access tokens and sessions in Databricks; the Databricks user isn't deactivated straight away (R19).
  • The pipeline's Databricks identity: keep the Databricks-native principal (proven end to end, outside the directory), or, if identities must be owned in Entra, an Entra service principal synced by AIM with the same GitHub federation policy (option C, proven at account level; run one full build with it before adopting). The original design, the provider signing in as a Google service account, is refused under Entra SSO (U0).

None of the requirements' options O1–O4 as written. This is O2 (Accounts API calls with both tokens) carried inside Terraform, so nothing is imported by hand and plans stay authoritative.

Verified

Everything in E2 marked ✅, from a pipeline on federation with SSO on, and then the whole design end to end (E1, End-to-end rebuild):

  • the pipeline's authentication recreated from bootstrap/ and checked hop by hop;
  • the lab torn down through the pipeline (workspace delete through the REST provider) and rebuilt in one pass from empty state, with no imports and no hand-copied identifiers; the next plans showed no changes;
  • clusters on back-end PSC only, workspace-level Terraform through the front end, and the workspace refused from the internet to one of its own admins.

Then on Entra SSO with AIM (E1, Entra SSO and AIM): the pipeline unaffected and the whole private deployment rebuilt with both on; people signing in privately through Entra with access from Entra groups, nested groups included, and others refused; a disabled person blocked without touching the pipeline; an Entra service principal synced by AIM signing in as the pipeline's identity.

Not verified: adding back-end PSC to an existing workspace, Unity Catalog objects at workspace level, the Entra-owned pipeline principal through a full build, and Entra-issued tokens for the pipeline (option B).

Configuration guide: Databricks on GCP from GitHub Actions with Terraform, own-IdP SSO (Entra ID and AIM), Private Service Connect

2026-11-14, verified by an end-to-end rebuild and on Entra SSO with AIM. End to end, in build order. The reference implementation (E5) is the lab repository; file names below refer to it. Placeholders: <org-id>, <ci-project>, <ws-project>, <account-id>, <owner>, <owner-id>, <repo>, <repo-id>, <region>.

0. Architecture

PlaneEndpointRuns onAuth
GCP infrastructureGoogle APIsGitHub-hosted runnerGitHub OIDC → Google workload identity federation → apply identity
Databricks accountaccounts.gcp.databricks.com (public, also with PSC)GitHub-hosted runnerGitHub OIDC → Databricks token exchange (automation principal), plus the apply identity's Google access token in X-Databricks-GCP-SA-Access-Token for workspaces, network configurations and endpoint registrations
Databricks workspace<workspace-id>.<n>.gcp.databricks.com, private once public access is offSelf-hosted runner in the users' networkGitHub OIDC → token exchange at the workspace's own endpoint, through the front-end PSC endpoint

Three Terraform stacks, each with its own state: GCP (repository root), Databricks account (databricks/), Databricks workspace (workspace/). A fourth root, bootstrap/, holds the pipeline's own authentication and is applied by administrators, not the pipeline.

1. Prerequisites set by administrators (once)

Items 1, 4 and 5 are one Terraform root, bootstrap/, applied locally by GCP and Databricks administrators with their own sign-ins; its outputs are the repository variables (AUTH_BOOTSTRAP.md). An identity can't be trusted to create itself, so the pipeline never applies it.

  1. CI project and workload identity pool for GitHub (Google: workload identity federation with deployment pipelines):

    • Provider issuer https://token.actions.githubusercontent.com; attribute mapping for sub, repository, repository_owner_id, ref.
    • Attribute condition on the owner's numeric ID and the repository name. Without a condition, any GitHub repository can mint tokens against the pool.
    • Apply identity: roles/iam.workloadIdentityUser for principalSet://…/attribute.ref/refs/heads/main. Plan identity: for principalSet://…/attribute.repository/<owner>/<repo>, read-only roles only.
    • State bucket: versioned, uniform access, public access prevention.
  2. Workspace project(s) with the APIs the stacks enable (Compute, DNS, IAP if used), and the apply identity's permissions there.

  3. Domain restricted sharing (if the organization restricts iam.allowedPolicyMemberDomains): a project-level exception adding Databricks' Google customer ID, with inherit_from_parent = true, narrowed by an enforced custom constraint that admits only:

    • the workspace service accounts in /roles/databricks.project., /roles/databricks.resource., /roles/databricks.network. roles;
    • the regional metastore credential in roles/storage.objectAdmin and roles/storage.insightsCollectorService.

    Set by an Organization Policy Administrator; the Org Policy API refuses user credentials without a quota project. Check it by creating a workspace: provisioning fails partway with an org-policy message if a grant is missing (R2, R3).

  4. Databricks automation principal (Databricks: GitHub Actions federation): a service principal, account admin (F6), with a federation policy:

    • issuer https://token.actions.githubusercontent.com;
    • subject repo:<owner>@<owner-id>/<repo>@<repo-id>:ref:refs/heads/main: GitHub issues the immutable-ID form; copy it from a first run's TOKEN_SUBJECT_INVALID error rather than typing it (R1). On a paid plan, prefer an environment subject with required reviewers;
    • audience: the default, the account ID.
  5. Repository variables (not secrets; nothing here is secret), from bootstrap/'s outputs: GCP_WIF_PROVIDER, GCP_APPLY_SA, GCP_PLAN_SA, TF_STATE_BUCKET, DATABRICKS_ACCOUNT_ID, DATABRICKS_CLIENT_ID (the principal's application ID). Then run auth-check, which shows each hop of the chain without printing a credential.

  6. Entra SSO and AIM (when people come from Entra; Databricks: automatic identity management):

    • Entra SSO for the account, then AIM on the same tenant (AIM requires it); Premium or Enterprise tier; identity-federated workspaces (new workspaces with a Unity Catalog metastore are).
    • Add each Entra group that should reach a workspace to the account from Entra (account console). Until then Terraform can't see it (R17).
    • Tenant policies apply to Databricks sign-in: a policy requiring MFA registration stops new or test users at Entra until they register or are excluded.
    • The pipeline's principal is unaffected by both (U1); nothing in steps 1–5 changes.

2. Pipeline

.github/workflows/terraform.yml, apply.yml:

  • Validate on every pull request and push: fmt, validate for each stack, Trivy.
  • Plan on pull requests as the plan identity (GCP stack only, -lock=false, no saved plan). On main as the apply identity, for each stack, saving plan.cache and the lock file as an artifact.
  • Apply by hand (workflow_dispatch) on main, given a plan run's ID: it checks that the run is a successful push to main whose commit main has moved past only with documentation, downloads that run's plan, and applies it. Apply the GCP stack before the Databricks one.
  • The first plan of a new setup runs on main. With an empty state bucket, init writes each stack's empty state and lock, which the read-only plan identity can't (R11).
  • Pin every action to a commit SHA; pin providers exactly where they're pre-1.0.

3. Account stack: the REST provider for header-requiring objects

databricks/rest.tf:

variable "databricks_token" {
  type      = string
  sensitive = true
  ephemeral = true
}

variable "gcp_access_token" {
  type      = string
  sensitive = true
  ephemeral = true
}

provider "restful" {
  base_url = "https://accounts.gcp.databricks.com/api/2.0/accounts/${var.account_id}"
  security = { http = { token = { token = var.databricks_token } } }
  header   = { "X-Databricks-GCP-SA-Access-Token" = var.gcp_access_token }
}

The job mints both in the step that runs Terraform: the Databricks token by exchanging the job's GitHub OIDC token (audience the account ID) at /oidc/accounts/<account-id>/v1/token; the Google token from google-github-actions/auth with token_format: access_token. A saved plan's apply must be given them again (ephemeral values aren't in the plan).

Resources (restful_resource), each with path, read_path = "<collection>/$(body.<id field>)", create_method = "POST":

ObjectCollectionNotes
VPC endpoint registration/vpc-endpointsBody vpc_endpoint_name, gcp_vpc_endpoint_info { project_id, psc_endpoint_name, endpoint_region }. Registration accepts the endpoint
Network configuration/networksBody gcp_network_info { network_project_id, vpc_id, subnet_id, subnet_region }, and for back-end PSC vpc_endpoints { rest_api = [...], dataplane_relay = [...] }. One per workspace; a failed workspace keeps it (R5)
Workspace/workspacesupdate_method = "PATCH", update_query = { update_mask = ["<changed fields>"] } (R4); poll_create and poll_update on body.workspace_status until RUNNING, pending PROVISIONING

Everything else at account level uses the Databricks provider on github-oidc (DATABRICKS_AUTH_TYPE=github-oidc, DATABRICKS_CLIENT_ID): private access settings, workspace permission assignments.

Ordering rule (R6): never remove an object and a workspace's reference to it in the same apply; detach first.

4. Private Service Connect

See ../PSC_SCENARIOS.md. For back-end PSC from creation:

  1. GCP stack: workspace VPC with a compute subnet and an endpoint subnet; two consumer endpoints (forwarding rules, load_balancing_scheme = "", no_automate_dns_zone = true) on Databricks' regional service attachments for the workspace (REST, plproxy-psc-endpoint-all-ports) and the relay (ngrok-psc-endpoint); a private gcp.databricks.com zone on that VPC with <region>.psc and the workspace URL and dp- name to the REST endpoint, and tunnel.<region> to the relay. (Databricks: Private Service Connect on GCP)
  2. Account stack: register both endpoints; network configuration listing them; private access settings; the workspace.
  3. Front end: an endpoint on the workspace attachment in the users' network, registered the same way; DNS for users by response policy (or conditional forwarding), not a whole-domain zone (R7): the workspace URL, dp- name and <region>.psc-auth to the front-end endpoint. Then private access settings with public access off.

5. Workspace stack on a self-hosted runner

Once public access is off, workspace-level Terraform runs inside the users' network:

  • Runner: a VM with no external IP, Cloud NAT for egress (GitHub, HashiCorp, Google's STS, the account API), the users' DNS. Run it as a dedicated user without sudo, with a label only the workspace workflow uses; prefer ephemeral runners (one job each) registered just in time by a GitHub App. scripts/register-runner.sh registers a long-lived one by hand for a lab.
  • Principal: workspace admin through a databricks_mws_permission_assignment in the account stack.
  • Provider: host the workspace URL, github-oidc. Token exchange and API calls go through the front-end endpoint.
  • Clusters: set an access mode (dedicated or standard), or a Unity Catalog workspace refuses them (R9).
  • Workspace URL from the account stack's state (terraform_remote_state), not copied. A script that needs it before the stack's first apply reads it with terraform console -plan (R13).

6. People and groups from Entra (AIM)

With Entra SSO and AIM, workspace access follows Entra groups. Two Terraform objects per group, in two stacks, both needed (R18):

# databricks/ (account stack): assign the group to the workspace
data "databricks_group" "workspace" {
  for_each     = var.workspace_groups             # { "<entra-group>" = ["USER"] }
  display_name = each.key
}

resource "databricks_mws_permission_assignment" "group" {
  for_each     = var.workspace_groups
  workspace_id = <workspace id>
  principal_id = tonumber(data.databricks_group.workspace[each.key].id)
  permissions  = each.value
}

# workspace/ (workspace stack, on the self-hosted runner): give it an entitlement
data "databricks_group" "entitled" {
  for_each     = var.group_entitlements           # { "<entra-group>" = { workspace_access = true } }
  display_name = each.key
}

resource "databricks_entitlements" "group" {
  for_each              = var.group_entitlements
  group_id              = data.databricks_group.entitled[each.key].id
  workspace_access      = each.value.workspace_access ? true : null
  databricks_sql_access = each.value.databricks_sql_access ? true : null
  workspace_consume     = each.value.workspace_consume ? true : null
}
  • Order: add the group from Entra; apply the account stack (assignment); apply the workspace stack (entitlement). An assignment alone lets members reach the workspace and then refuses them: "not assigned or no Workspace access entitlement" (R18). In a new workspace the built-in users group carries no entitlement to fall back on.
  • Entitlements unset unless true: the provider refuses workspace_consume next to workspace_access or databricks_sql_access, even when one of them is false.
  • Nested groups: members of a group nested inside an assigned group get access, but the nested group itself isn't visible to the API or Terraform (R17). Assign the parent.
  • Users are created at first sign-in and linked to Entra a few minutes later; nothing to manage in Terraform.
  • Private sign-in: with public access off, people reach the workspace only through the front-end endpoint (their network's DNS to it); from the internet they are refused after signing in (U4). To test it from outside the network, a browser on an SSH SOCKS proxy through a VM in the users' network, with DNS resolved on the VM's side, shows the private path.
  • Leavers: disable in Entra (sign-in stops at once) and revoke personal access tokens and sessions in Databricks: the Databricks user isn't deactivated straight away (R19).
  • The Entra groups themselves (and nesting) as Terraform: examples/entra/ (groups.tf).

7. Optional: the pipeline's identity from Entra (option C)

If the pipeline's Databricks identity must be owned in Entra (AIM assessment); proven at account level (R16), not yet through a full build:

  1. An Entra app registration with no secret and no API permissions, and its service principal.
  2. Add it to the account from Entra (account console). Its Databricks application ID is the Entra client ID.
  3. Give it account admin, and a service principal federation policy with the same issuer and immutable-ID subject as step 1.4. With the Databricks CLI on Windows PowerShell 5.1, pass JSON bodies as --json @file: inline JSON is mangled.
  4. Set DATABRICKS_CLIENT_ID to its application ID; auth-check (with client_id) shows it signing in.

Terraform can't create this principal in Databricks; it can manage it by application ID once provisioned. examples/entra/ (pipeline_principal.tf) does steps 1 and 3 as Terraform, with the provisioning step between two applies; it also holds an untested option B. The Google side (the apply identity and the header) is unchanged.

9. Teardown

Mind the account's daily workspace creation limit (R15) before tearing down and rebuilding on the same day. Workspace stack, then account stack, then GCP stack, each a reviewed plan -destroy applied by hand; apply only the newest destroy run (another apply in between makes it stale). In the account stack, workspaces go first (polled until 404), then their network configurations and registrations. Between the account and GCP stacks, delete what Databricks left in the project (R10): the db-<vpc>-<region>-ingress firewall rule on each workspace VPC, which blocks deleting the VPC, and by decision the workspace buckets. The organization's DRS exception and the principal are removed by their owners afterwards. With AIM, also remove the groups and principals added from Entra (and any users it created) from the account; they stay after a workspace is deleted. See E7.

E3

Identity design

2026-11-14, after the end-to-end rebuild and the Entra SSO and AIM tests. Every identity the pipeline and its operators use, what each trusts, what it holds, and why. No identity has a key or a stored secret: GitHub's OIDC token is exchanged for short-lived Google and Databricks credentials in each job.

How a job authenticates

Steps 1–6 are google-github-actions/auth; steps 7–10 are what the Databricks provider does itself with auth_type = "github-oidc". Workspace-level calls exchange the same kind of token at the workspace's own endpoint (https://<workspace>/oidc/v1/token). The trust in every note is created once by bootstrap/ (see AUTH_BOOTSTRAP.md); auth-check runs the chain and shows each hop's result without printing a credential.

Why these boundaries

  • Owner ID and repository name in the Google pool's condition: a deleted account's name can be registered again; its numeric ID can't.
  • main only for the identities that can write: a free private repository has no branch protection or environment reviewers, so the collaborator list is the real boundary. On a paid plan, bind the apply identity and the federation policy to a GitHub environment with required reviewers instead of the branch (Databricks recommends the Environment entity type).
  • The subject's immutable-ID form (R1): bootstrap/ builds it from the numeric IDs; otherwise copy it from a real token or a first run's TOKEN_SUBJECT_INVALID error.
  • Created by administrators, not the pipeline: an identity can't be trusted to create itself. bootstrap/ is Terraform with its own state in an administrators' bucket, applied locally with their sign-ins; its outputs are the repository variables.
  • Native or Entra-owned pipeline principal: the native one (in the Databricks account only) is independent of the directory; the Entra-owned one (option C) puts ownership, reviews and disabling in Entra, with the same narrow GitHub trust. Exchanging Entra-issued tokens instead (option B) would bring Entra Conditional Access to the pipeline, but needs an account-wide federation policy trusting the tenant; untested.
  • Self-hosted runners use the same identities: their jobs get GitHub OIDC tokens like hosted ones. Hardening option: require assertion.runner_environment == "self-hosted" in the pool condition for an identity used only by the workspace stack.

Findings beyond the hypotheses

#Finding
R1GitHub's OIDC subject for the repository was the immutable-ID form, repo:<owner>@<owner-id>/<repo>@<repo-id>:ref:<ref>. A federation policy with the name-only form fails with TOKEN_SUBJECT_INVALID, which names the subject the token carries
R2Domain restricted sharing refuses classic workspace provisioning's grants to Databricks-owned service accounts. A narrowed exception, set by an organization policy administrator, is a prerequisite per workspace project
R3Provisioning makes four kinds of grant to Databricks accounts (two project roles, a network role, and two storage roles on the workspace's default Unity Catalog bucket); a narrowed DRS profile must admit all four
R4A workspace update through the Accounts API needs an update_mask query parameter naming the changed fields; without it, 400 Update mask must be specified
R5Deleting a failed workspace doesn't release its network configuration; a retry needs a new one
R6Removing an object and the workspace's reference to it in one apply can make Terraform delete the object first; Databricks refuses while it's attached. Detach in one apply, delete in the next
R7A private gcp.databricks.com zone in a users' or CI network makes accounts.gcp.databricks.com unresolvable there. Use a DNS response policy (or conditional forwarding) for the workspace names only
R8An unauthenticated request can't test private access: the network check comes after authentication (303 to login, 401 on the API, from the internet as from inside)
R9A Unity Catalog workspace refuses clusters without an access mode ("NO_ISOLATION … not allowed")
R10Deleting a classic workspace leaves an ingress firewall rule on its VPC (which blocks deleting the VPC), its three buckets, Databricks' custom roles and grants, and the databricks-compute service account in the project. See E7
R11With an empty state bucket, a pull request's plan fails at terraform init as the read-only plan identity: init writes each stack's empty default state and its lock. The first plan of a new setup has to run on main, as the apply identity
R12With public access off, the workspace's own token endpoint still answers from the internet and issues a token; the refusal comes at the API: 403 "Unauthorized network access to workspace: <workspace-id>". The same principal, through the front-end endpoint, gets 200
R13terraform console evaluates against state, so on a stack's first run a terraform_remote_state output reads as (known after apply). Scripts that need it before the first apply should use terraform console -plan
R14At account level, destroying a databricks_service_principal only deactivates it unless disable_as_user_deletion = false; its role and federation policy are deleted. The reference bootstrap/ now sets it, so a teardown leaves no principal behind
R15A Databricks account has a daily limit on workspace creation. Past it, POST /workspaces returns 429 with RESOURCE_EXHAUSTED: Limit reached for workspace creation. You've hit your daily limit for workspace creation. Please try again in 24 hours. A teardown and rebuild on the same day, on an account where other work also creates workspaces, can use it up; the error doesn't say the number. Terraform state stays consistent: the next plan holds only what wasn't created. The pipeline's summaries now show the API's message, not just the first line of the error
R16An Entra service principal synced by AIM keeps its Entra client ID as its Databricks application ID, can hold account admin, and can carry its own service principal federation policy; a GitHub token exchanged against that policy signs in as it. See USE_CASE_RESULTS.md, U7
R17With AIM, a group added to the account from Entra is visible to the account API (with its external ID); a group nested inside it is not; users and member counts appear only once people sign in. Terraform can assign workspaces only to directly added groups. See USE_CASE_RESULTS.md, U3
R18Assigning a group to a workspace at account level (permission assignment, USER) lets its members in but gives the group no entitlement; in a new workspace the built-in users group carries none either. Members then reach the workspace and are refused: "not assigned to the workspace or no Workspace access, Databricks SQL access or Consumer access entitlement". The group needs an entitlement set inside the workspace (databricks_entitlements, workspace stack). AIM's membership does reach the workspace: the member's workspace record lists the group. See USE_CASE_RESULTS.md, U4
R19Disabling a person in Entra stops them at Entra's sign-in ("Your account has been locked"), but AIM doesn't deactivate the Databricks user straight away: minutes later the account record still read active. Anything that doesn't pass through Entra sign-in, an open session or a personal access token, isn't stopped by the disable alone. See USE_CASE_RESULTS.md, U5

R10. Deleting a classic workspace leaves Databricks-created objects in the customer's project: an ingress firewall rule on the workspace's VPC (db-<vpc>-<region>-ingress), the workspace's three buckets, three custom roles and their grants. The firewall rule blocks deleting the VPC.
